# RAE: instructions for agents

RAE is a bounty-hunter-vs-outlaws Minecraft Bedrock addon. TypeScript source in `rae/src` compiles into the behavior pack. You are working on the ARCH (Foundations) epic: a behavior-preserving refactor that adds shared core modules. **Do not change game behavior or any number unless your brief says so.**

## Layout

```
rae/src/config/    numbers and coordinates only          rae/test/       tests (run the COMPILED code under a fake game API)
rae/src/logic/     pure rules, no game imports           rae/scripts/    test runner and legacy ratchet
rae/src/core/      shared engines and contracts          your_pack_name_BP/   behavior pack (scripts/ is BUILD OUTPUT, gitignored)
rae/src/systems/   one file per gameplay system          BountySys_RP/   resource pack
rae/src/main.ts    imports + debug commands              docs/test-cards/   one manual test card per task
```

`rae/test/layers.test.mjs` enforces the layer rules below from the source, so a bad import fails `npm test`.

## Commands (run from `rae/`; run `npm ci` once in a fresh worktree)

| Command | What it does |
|---|---|
| `npm run check` | type-check (`tsc --noEmit`) |
| `npm test` | compile to `.test-build/`, install the fake API, run `node --test` |
| `npm run check:legacy` | fails if a legacy-pattern count is higher than on `main` |

## The seven rules

1. Layers point down: `config <- logic <- core <- systems`. `src/logic/` has no game imports.
2. Systems never import each other, only `core/` contracts and events.
3. Numbers and coordinates live only in `config/`. (One deliberate exception: a robbery a builder authors in game is world data, saved in the world like the recorded train route. `config/balance.ts`'s `ROBBERY` block holds only its caps, defaults and tuning.)
4. Mutable game state lives in `core/state`, not in module variables or tags. Tags are output for command targeting.
5. One writer per channel: `core/ui` (title/action bar/chat), `core/sound`, `core/log`, `core/director` (events).
6. A system self-registers with `registerSystem`; adding one edits no shared file.
7. Every change ships a machine-checkable test.

## How you work

- You are in your own git worktree on branch `task/<ID>`. Commit there. **Never push, tag, or touch other branches.**
- Edit only the paths in your brief ("allowed paths"). **Never edit:** manifests (`*/manifest.json`), `README.md`, `ARCHITECTURE.md`, `MIGRATION.md`, `rae/package.json`, `rae/package-lock.json`, `rae/test/fake/*`, `rae/scripts/*`, `.github/`, `CLAUDE.md`, unless your brief names the file. If you need one changed, say so in your report.
- **Public script-event ids are an API** (command blocks in the world call them): `bounty:start_round`, `bounty:teleport`, `bounty:fort`, `bounty:ranch`, `bounty:train`, `bounty:escape`, `bounty:lockpick`, `bounty:test_capture`, `rae:adopt`, `rae:aim_spike`, `rae:debug`, `rae:log_debug`, `rae:menu`, `rae:npc`, `rae:npc_probe`, `rae:probe_damage`, `rae:reset`, `rae:robbery_probe`, `rae:tumbleweed`, and the train recorder `rae:train_mark`, `rae:train_station`, `rae:train_undo`, `rae:train_clear`, `rae:train_loop`, `rae:train_info`, `rae:train_show`, `rae:train_spike`. Never rename or remove one. (`rae:log_debug` is registered directly on the raw engine signal by `core/log.ts`, not through `core/events.ts`'s `onScriptEvent`/`listScriptEvents` registry — log.ts cannot import `core/events.ts` — so it is real but does not show up in `rae:debug`'s event list.)
- **Public custom-command ids are an API too, a separate mechanism from script events**: `systems/liveconfig.ts` registers `rae:config_list`, `rae:config_get`, `rae:config_set_number`, `rae:config_set_bool`, `rae:config_set_coordinate`, `rae:config_reset` via `@minecraft/server`'s `CustomCommandRegistry` (`system.beforeEvents.startup`), not `core/events.ts`. Real slash commands (`/rae:config_set_number ...`, no `/scriptevent` prefix), each operator-only via `CommandPermissionLevel.GameDirectors`, each with a `field` parameter the game's own command bar tab-completes from an enum built off `core/configoverrides.ts`'s registry. Never rename or remove one. `systems/robberyprobe.ts` registers one more, `rae:robbery_probe_ctx` (Phase 0 of the in-game robbery framework, a measurement). The framework's builder wand is the item `bountysys:robbery_wand`, and `systems/robberybuilder.ts` registers fifteen operator-only commands: `rae:robbery_list`, `rae:robbery_info`, `rae:robbery_new`, `rae:robbery_select`, `rae:robbery_delete`, `rae:robbery_start`, `rae:robbery_stop`, `rae:robbery_reset`, `rae:robbery_activate`, `rae:robbery_wand`, `rae:robbery_edit`, `rae:robbery_view`, `rae:robbery_undo`, `rae:robbery_area`, `rae:robbery_set` (and the enum `rae:robbery_setting`). `start`, `stop`, `reset` and `activate` take a robbery id and work from a command block or an NPC button, which is how an old command-block build hands part of itself to the framework. Every id the framework adds is `rae:robbery_*` / `bountysys:robbery_*`, the same never-rename rule. The NPC shop system registers fifteen more operator-only commands from `systems/shopbuilder.ts`, through `core/commands.ts`: `rae:shop_list`, `rae:shop_info`, `rae:shop_new`, `rae:shop_sell`, `rae:shop_buy`, `rae:shop_trade`, `rae:shop_service`, `rae:shop_edit`, `rae:shop_open`, `rae:shop_select`, `rae:shop_copy`, `rae:shop_place`, `rae:shop_move`, `rae:shop_delete`, `rae:shop_undo` (same never-rename rule). `rae:npc` is what a shop NPC's dialogue button runs; `rae:npc_probe` is the NPC measurement. `test/load-smoke.test.mjs` registers every public command together under the validating registry, so a bare name or two systems claiming one name fails a test instead of silently in the game. Engine facts for it: a `world.beforeEvents.*` callback is read-only (anything that changes the world must be deferred with `system.run`), and a registered enum or command name needs a namespace even where the typings do not say so.
- Write **characterization tests before refactoring** anything whose behavior you touch (tick cadences, death-handler order, round flow, jail rotation, compass output), watch them pass on the old code, then refactor.
- **Definition of done:** `npm run check` clean, `npm test` green, `npm run check:legacy` not raised, diff inside allowed paths, and a manual test card at `docs/test-cards/<ID>.md`: numbered in-game steps, expected result, and the content-log line to look for. For risky logic, break it on purpose (a mutation) and confirm a test fails.
- **Report (<= 200 words):** what changed, files touched, test/check results, anything you could not verify, anything the orchestrator must decide. Do not claim it works in-game; you can't run the game.

## Testing with the fake API

Tests import the compiled game code plus a fake `@minecraft/server`. See `rae/test/helpers.mjs` and any existing test. The essentials: `fake.makePlayer(name, { tags, location, holding, facing })`, `fake.advance(ticks)` (time only moves when you move it), `world.afterEvents.<name>.emit(payload)` and `system.afterEvents.scriptEventReceive.emit({ id })` to deliver events, `fake.dimension("overworld").played` for sounds, `fake.calls` for query counts, `checks()` to collect failures. A feature branch should not edit `test/fake/*`: extend behaviour inside your test file, or say what is missing. On the main line additive, opt-in extensions to the fake are fine when a feature needs them, and the existing ones are worth using: a block store (`fake.placeBlock`, `dim.getBlock` with real permutations and containers, `fake.setUnloaded`, `fake.pairChests`), `fake.strictBefore = true` (every `world.beforeEvents.*` handler and custom-command callback then runs in RESTRICTED execution, so a forbidden call throws as it does in the game), `fake.startUp()` (a custom-command registry that enforces namespaced names, enums registered before their commands, startup-only registration, typed arguments and the permission level, with `run(name, origin, ...args)` to act out typing a command), `useBlock(player, [x, y, z], { held })` in `helpers.mjs` (a right-click as the before event reports it), and `test/fake/minecraft-server-ui.mjs`'s function responses (a queued response may be a function of the form shown, so a test presses "the button called Locks"; `test/robbery-ui.mjs` is a stand-in player built on it). `test/fake-harness.test.mjs` pins them. Also additive and opt-in, for the shops: `makePlayer(name, { inventory: true })` (a real 36-slot bag that answers COPIES, as the engine does, so code that forgets `setItem` fails), `ItemStack` with enchantments, potions (`Potions.resolve`), `isStackableWith` and per-kind stack limits, `dim.spawnedItems`, `player.aimEntities`; `test/fake-items.test.mjs` pins them. For the shops' services: `EffectTypes`, `EnchantmentTypes` and `EntityTypes` (looked up with or without `minecraft:`; a test that wants a game strict about the prefix swaps `.get` for the length of the test), `TicksPerSecond`, `fake.effects` / `fake.entityTypes` (the ids the game knows), `player.effects` and `removeEffect`, a `minecraft:tamemount` component on the horse family, `canAddEnchantment`, and `player.teleportLog` with teleports across dimensions. For moving an NPC from an area nobody is near: `fake.hideUnloadedEntities = true` makes a query miss every entity in a stretch `fake.setUnloaded` marked until a ticking area that has FINISHED loading covers it, with `fake.tickingAreaDelay` (ticks a new area takes to load), `fake.tickingAreaFails` (a message every new area is refused with), `fake.tickingAreaCapacity` (chunks that fit) and `world.tickingAreaManager.hasTickingArea`; all reset by `fake.reset()` and off by default. For item frames: `fake.setFrameItem(dim, pos, typeId, amount)` and `fake.frameItemAt` (what a frame block shows), `fake.punchFrame(player, dim, pos, options)` (an ASSUMED punch: the item pops out as a dropped item, with `entitySpawn` and the signals you choose; the options let a test model a game that sends other signals, in another order, or none), structures that save the frames in their box with what each shows and bring them back on `place` (`fake.structureFrames`), and `fake.passableBlocks` (type ids the default ray looks through unless it is asked with `includePassableBlocks`); `test/robbery-frame*.test.mjs` pin them.

## Engine facts: verify, never guess

This targets a very recent Bedrock build (`1.26.x`); schemas and APIs drift, and guessing has cost whole sessions. Check `rae/node_modules/@minecraft/server/index.d.ts` for any API you use, and the game's own data at `C:\XboxGames\Minecraft for Windows\Content\data\resource_packs\` (for example `vanilla\sounds.json`, `vanilla\font\`). If something can't be verified, write a spike/finding instead of assuming.

Known gotchas (details in `README.md`):
- In an `entityDie` handler the dead entity can already be invalid: `hasTag()` throws `InvalidEntityError`. `typeId`, `id` and `scoreboardIdentity` still work. Guard with `isValid`.
- Item dynamic properties are refused on stackable items, but a custom item with `"minecraft:max_stack_size": 1` accepts them (measured 2026-10-06 on `bountysys:robbery_wand`); the guns still keep per-item state in Maps.
- Block interaction (measured 2026-10-06, `docs/test-cards/ROBBERY-SPIKE.md`): `world.beforeEvents.playerInteractWithBlock` fires for every right-click on any block and `cancel = true` stops containers, levers, buttons and wooden doors WITH THE WAND IN HAND (the only case the spike measured: every `cancel` row in its matrix is a wand row, and the empty-hand rows say "cancel untested"; a 2026-10-06 playtest then reported a sealed chest still opening for a click that was not the wand's, so empty-hand cancel on a container is UNVERIFIED until `/scriptevent rae:robbery_probe cancel interact on` is run empty-handed); it repeats while the button is held, so gate on `isFirstEvent`. A click on pure AIR with a plain custom item was never measured either (the spike's one "air" swing was probably aimed at an entity or a passable block): the guns rely on a LEFT-click in the air, a swing with source `Attack`, so use that, or sneak plus a block, rather than a right-click in the air, for anything that has to work. A swing is reported with only SOME block clicks (the spike's log: a chest 5 times in 8, a wooden door 4 in 6, a button or lever 1 in 3, an iron door or iron trapdoor never) and at no fixed moment relative to the block event, so a swing or item use is only a "click on nothing" when `player.getBlockFromViewDirection` finds no block within reach; a time window alone let the first playtest open a second menu on top of the block's screen. The after event only fires when the interaction does something. A before-event or custom-command callback is restricted: `spawnEntity`, `runCommand`, `setPermutation`, `spawnParticle` and `addTag` throw there, so defer world changes with `system.run` (`sendMessage`, dynamic properties, `getLootTable` and `getBlock` are fine).
- NPCs (typings read 2026-10-07, then MEASURED in the game the same day on BP 0.2.0, `docs/test-cards/NPC-PROBE.md`): the installed `@minecraft/server` has no dialogue API and no NPC component class. The only NPC traces are `ScriptEventSource.NPCDialogue`, an `initiator` (the player) next to `sourceEntity` (the NPC) on a script event or custom-command origin, and `world.beforeEvents.playerInteractWithEntity` (`cancel`, `itemStack`, `player`, `target`; a restricted callback). A dialogue scene's buttons are static JSON in `your_pack_name_BP/dialogue/` and run as the NPC with `@initiator` the player, so a script cannot write an NPC's buttons: a shop is data plus a form. `core/events.ts` hands a script-event handler an `origin` (`fromNpc`, `entity`, `initiator`) as a third argument; the first argument is still only ever the source when that is a player, so for an NPC's button it is `undefined`. Measured (content log `[npc-probe]` lines): a right-click on a `minecraft:npc` reaches `playerInteractWithEntity` before and then after, and `cancel = true` in the before event stops the game's own NPC screen, operator included (5 of 5 cancelled clicks showed nothing and the after event never fired), so a script can take a click over; without a cancel the owner saw an edit-style screen first and, after clicking in it, the scene's own box. `getComponent("minecraft:npc")` answers `undefined` without throwing, so a script cannot set an NPC's skin. `npc.runCommand("dialogue change @s <scene>")` does not throw right after spawning or 10 ticks later and the scene is in effect, and `player.runCommand("dialogue open <selector> @s <scene>")` opens the scene with no click. A scene button's `/scriptevent` arrives with `sourceType` NPCDialogue, `sourceEntity` the NPC and `initiator` the player, and a second command in the same button (a `tag`) runs too. An NPC's `nameTag`, entity dynamic property and tag survive leaving and re-entering the world. Not measured: whether the scene assignment survives that, what a non-operator sees, and how a name shows above the head.
- Shop services (built 2026-10-07; NOT yet run in the game, see `docs/test-cards/NPC-SHOP.md`): a deal's effect, enchantment, tame mount and teleport are done by `core/shopservices.ts`, split into `prepareService` (reads only: does the game know the id, does the customer hold something the enchantment fits) and `apply`/`undo`, so `core/shoptrade.ts` can prepare every service before a coin moves and undo the ones already done if a later one throws. They run in a form's answer, never in a before-event. Which of `EffectTypes.get`, `EnchantmentTypes.get` and `EntityTypes.get` want the `minecraft:` prefix is unmeasured, so a lookup tries the id as typed and then with the prefix. `canAddEnchantment` may answer false or throw for an enchantment that does not fit; both are handled. `Container.getItem` answers a copy, so an enchanted item only lands when the changed stack is put back with `setItem`.
- Moving a shop NPC from an area nobody is near (built 2026-10-07; NOT yet run in the game, see `docs/test-cards/NPC-SHOP.md` steps 29 to 36): a script cannot see an entity in an unloaded chunk, so `core/shopnpc.ts` keeps where each shop's NPC was last put or seen in a world property (`rae:shop:at:<id>`), and to bring it creates a temporary ticking area with `world.tickingAreaManager.createTickingArea(id, { dimension, from, to })` (the typings say its promise returns "when all the chunks in the area are loaded and ticking"; Phase 0 measured only that a script ticking area can be created, not that an entity query then sees entities in it), looks for the NPC with `Dimension.getEntities` for up to a second, teleports it to the builder and removes the area. A new NPC is made only when the remembered place loaded and held none; if the area will not load nothing is made, because making one then would duplicate an NPC that is merely out of sight. `createTickingArea` and `removeTickingArea` are `no-restricted-execution`, so this runs from `system.run` or a form's answer. Ticking areas made by script do not survive leaving the world (measured), so a crash mid-fetch leaves nothing behind after a relaunch.
- The typings tag every method that cannot run in a before-event or custom-command callback with `@privilege no-restricted-execution`, and the list is long: besides world changes it covers `Player.playSound`, `Dimension.playSound`, `ScreenDisplay.setActionBar` and `setTitle`, `Entity.addEffect`, `kill`, `teleport`, `applyDamage`, `Container.addItem`, `setItem` and `clearAll`, and structure calls. Reads, `sendMessage`, `world`/`Entity` dynamic properties and `LootTableManager` are exempt. So such a callback decides and cancels, then hands everything else to `system.run`; `fake.strictBefore` enforces this in tests.
- `BlockPermutation.getState` does exist (`index.d.ts`); setting a door's `open_bit` on both halves holds. A robbery element's blocks are bound by position, so an unloaded chunk means "not now": `core/robberyworld.ts` answers undefined or false and the janitor retries when the chunk loads.
- Item frames (built 2026-10-07 for the robbery framework; NOT yet run in the game, see `docs/test-cards/ROBBERY-FRAME.md`): a frame (`minecraft:frame`, `minecraft:glow_frame`) is a BLOCK with a block entity, not an entity, and `@minecraft/server` 2.10.0 has no item-frame API, so a script can neither read nor set what a frame shows. The only thing that puts an item back in one is a saved structure, so a robbery frame's loot is set on the element (never read from the frame), `core/robberyworld.ts` empties a frame with `setType("minecraft:air")` then `setPermutation(original)`, and it keeps one one-block World-mode structure per bound frame, `rae:rb_<robbery>_<x>_<y>_<z>` (negatives written `m<n>`; `ROBBERY.frameStructurePrefix`). Those ids are saved in worlds: never rename the prefix. `createFromWorld` needs an unused id (delete first) and silently saves air over an unloaded chunk, so `captureFrame` checks the chunk first. A punch can be SEEN and not cancelled (only `playerBreakBlock` and `playerInteractWithBlock` have before-events), so `world.afterEvents.playerStartBreakingBlock`, `entityHitBlock` and `entitySpawn` are the evidence and `frameHit` undoes the punch a moment later; the live switch `robbery.guardFramePunches` turns that off. Because a frame can never be read, a run notes EVERY frame of its robbery for the janitor when it starts (`noteFrames`) and so does `resetSiteNow`, so the end of a run re-places each from its saved copy whatever happened to it, and `core/robberyedit.ts` refuses to save a frame that is waiting to be put back (it may be empty). MEASURED 2026-10-08 (the owner, BP 0.2.1): a structure placed OVER a frame already standing there filled it (the item could be taken) but nobody could see the item, so `restoreFrame` now clears the frame first and places the copy as a new block (suspected cause: the data is loaded in place and no screen is told; the fix is unverified in the game, and `fake.strictFrameSync` models the suspicion). UNMEASURED: that a right-click on a frame is reported as `playerInteractWithBlock` and is cancellable, which events a punch sends and whether the popped item arrives as an `entitySpawn`, whether the air-then-permutation swap drops the item, and whether the default `getBlockFromViewDirection` ray looks through a frame (`systems/robberybuilder.ts` asks again with `includePassableBlocks` and trusts that second answer only for a frame).
- Guards (built 2026-10-08; NOT yet run in the game, see `docs/test-cards/ROBBERY-GUARDS.md`): a robbery's `spawn` effect makes mobs with `Dimension.spawnEntity(type, {x + 0.5, y, z + 0.5})` and tags each `rbg` (every guard) and `rbg:<robbery>` (whose). `core/robberyworld.ts` removes them with `getEntities({ tags })` + `remove()` in every dimension when the site is put back, and a stray sweep removes any guard whose robbery has no run, on `world.afterEvents.entityLoad` and once ~40 ticks after start-up (guards already in loaded chunks do not fire `entityLoad`, the same as `systems/transit.ts`'s cars). `EntityTypes.get` answers whether the game knows a mob (tried as typed, then with `minecraft:`; which form the real game wants is unmeasured). Unmeasured: how a script-spawned pillager is equipped and behaves, whether `remove()` reaches every guard, what `entityLoad` reports for a chunk coming back.
- `Dimension.playSound` throws for pitch < 0.01 or volume < 0.
- The game's font has no arrow or geometric-shape glyphs; use ASCII plus `« »`.
- Player-list queries (`getAllPlayers`, `getPlayers`) cost real time per call; prefer one shared snapshot per tick.
- `system.runTimeout` callbacks must re-check `player.isValid` for anything that outlives the tick.
