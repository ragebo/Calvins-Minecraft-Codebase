# Calvins-Minecraft-Codebase

RAE (Red Alive Escape) — a bounty-hunter-vs-outlaws Minecraft Bedrock addon. Originally
built as flat V1 JavaScript, since ported to a structured TypeScript project (`rae/`)
that compiles into the behavior pack.

## Layout

```
rae/                    TypeScript source. This is what you edit.
  src/config/           Every coordinate (world.ts) and every tunable number (balance.ts),
                         plus gun/ammo stats (guns.ts). Nothing else defines these values.
  src/logic/            Pure rules with no game imports, so they can be tested outside MC:
                         bearing.ts    direction math + bearing-bar rendering for the law compass
                         schema.ts     versions the config so saved data is never misread
                         route.ts      the train's track: recording, curve smoothing, distance along
                                       it, heading, speed profile, steering a body onto it
  src/core/             Shared engines and contracts the systems build on:
                         registry.ts   system registration + round reset
                         events.ts     one entityDie / playerSpawn / scriptEventReceive
                                       dispatcher, with handlers in a defined order
                         tick.ts       the one polling loop; every repeating job is an onTick handler
                         state.ts      one record per player (role, jail, elimination, ammo) that
                                       game logic reads; role tags are written from it, for command blocks
                         players.ts    cached "who is law / a free outlaw / a prisoner" queries
                         ui.ts         titles, the action bar (with priorities) and chat; the compass
                                       posts through it
                         director.ts   the one slot fort raid / ranch raid / train robbery share
                         economy.ts    the only file that touches coins/bounty
                         raid.ts       shared wave-spawn engine (used by the fort raid)
                         round.ts      round lifecycle state machine (a contract: no system uses it yet)
                         persist.ts    contract for state that survives a reload (nothing registers yet)
  src/systems/          One file per gameplay system (see below). Each registers itself
                         via registerSystem() and is imported once from main.ts.
  test/                 Tests. They run the compiled code under a fake game API.
  scripts/              The test runner, the legacy-pattern ratchet, and gen-train-model.mjs
                         (writes the train's model and texture into the resource pack).
  MIGRATION.md          The rules this port followed, for reference.

your_pack_name_BP/      The behavior pack. scripts/ is BUILD OUTPUT — never edit it by
                         hand, it's regenerated by `npm run build` and gitignored.
  items/                Data-driven item definitions (guns, ammo, law compass)
  entities/             bountysys:bullet (the shared projectile all projectile guns spawn) and
                         bountysys:train_car (the rideable train car)
  loot_tables/, manifest.json

BountySys_RP/           Resource pack: the revolver and law-compass icons, and the bullet's
                         client entity definition.
                         sounds/ (music) is gitignored — not included here, licensing unconfirmed.

docs/test-cards/        One manual in-game test card per architecture task.
CLAUDE.md               Rules for agents working in this repo (layers, the seven rules, checks).
```

The systems are still being moved onto these core modules. `npm run check:legacy` counts what
is left of the old style (direct role-tag reads, private timers, errors sent straight to chat)
and fails if a count goes up.

## Systems (`rae/src/systems/`)

| File | Owns |
|---|---|
| `roles.ts` | Round-start law/outlaw assignment, role spawn teleport |
| `jail.ts` | Jail site tracking, capture → bounty payout → jail → elimination |
| `jailbreak.ts` | Lockpick minigame, escort-vulnerability after a rescue |
| `raids.ts` | Fort raid (via the shared `raid.ts` engine) + ranch raid (hand-rolled — its dynamic reinforcement timer and per-mob rules don't fit the shared engine without changing behavior) |
| `train.ts` | Train robbery: movement, bridge demolition/rebuild, vault, guards |
| `aimprobe.ts` | Measurements for the planned gun controls (left-click fire, held right-click aim with zoom and a scope overlay, off-hand-swap reload): logs what the game reports, drives the zoom and the overlay; changes no gun |
| `transit.ts` | The scripted train: route recorder and a rideable car driven along the route (slice 1, a spike; the robbery moves onto it in a later slice) |
| `boat.ts` | Outlaw win condition (gang escapes by boat) |
| `economy-rules.ts` | Death coin loss/inventory drop, villager robbery |
| `horse.ts` | Horse speed standardization |
| `gold.ts` | Gold item → coins conversion |
| `guns.ts` | The 6-gun weapon system — see below |
| `endgame.ts` | Law win condition: every outlaw eliminated **or in jail** (a jailed gang has nobody left free to run a jailbreak) |
| `compass.ts` | Law compass — see below |

Fort raid, ranch raid and train robbery all go through `core/director.ts`, so only one
of them can run at a time. Jailbreak is deliberately not part of it: it's a
continuous system, not a scripted set-piece.

### Roles, state and tags

Who is law or outlaw, who is jailed or eliminated, and who has won live in one record per
player in `core/state.ts`; game logic reads that record. The matching tags (`law`, `outlaw`,
`eliminated`, `jailed`, `in_jail`, `send_to_jail`, `escort_vulnerable`, `winner`) are written
from it as output, so command blocks can keep targeting `@a[tag=law]`.

Tags typed by hand come back the other way: `/tag @s add law` (or `outlaw`, `eliminated`, ...)
updates the record within a second, and adding one role's tag to a player who has the other
switches them and takes the old tag off. `/scriptevent rae:adopt` does the same check for
everyone right now and lists what each record says. It only changes what the game believes: it
does not run the side effects of a role (no gamemode change, no teleport, no kit). A record with
a change of its own still waiting to be written is left alone until it is written.

### Gun system

6 guns in `src/config/guns.ts`, one shared firing engine in `src/systems/guns.ts`:

- **Handguns** (projectile): revolver, pistol
- **Rifles** (projectile): bolt-action (single shot, long reload), semi-auto
- **Shotguns** (true hitscan, not projectile): pump, double-barrel

Ammo is per weapon category (handgun/rifle/shotgun rounds), real inventory items.

**Controls** (built for riding: a horse takes sneak, which dismounts and reports nothing):

| Action | How |
|---|---|
| Fire | Left-click (at the air, a mob or a block) |
| Aim | Right-click toggles it (tap on, tap off): a bow-like zoom, and a scope overlay for the bolt rifle. You walk slower while aimed, and can fire while aimed. It ends by itself if you switch slot, die or leave |
| Reload | Q. The game drops the gun; a script takes it back into its slot and starts the reload |
| Reload (automatic) | Clicking an empty gun clicks and reloads it |

How each of these works, and what the game really reports for them, is in
`docs/test-cards/AIM-SPIKE.md` (measured) and `docs/test-cards/GUN-CONTROLS.md`. Aiming lives in
`core/aim.ts` (the zoom and the scope overlay); the zoom per gun is `aim.fov` in `config/guns.ts`.

Projectile guns spawn a shared `bountysys:bullet` entity and
apply damage on hit via script (not the entity's own vanilla damage) so each gun's
number is independent. Shotguns jitter several rays per trigger pull via
`Dimension.getEntitiesFromRay` for real per-pellet spread.

Every gun is a flat 2D item held like a tool (`minecraft:hand_equipped`) with its own
texture (`BountySys_RP/textures/items/<gun>.png`, 16x16, mapped in
`textures/item_texture.json`). The revolver used
to be a 3D model with an attachable; that is still in git history
(`git show 6661ecb:BountySys_RP/attachables/revolver.json`) if it is ever wanted back.
`npm test` checks that the two packs agree with each other (`assets.test.mjs`).

Every gun has its own fire sound and a timed reload sequence, all vanilla sound events,
defined per gun in `src/config/guns.ts` (`sounds.fire` / `sounds.reload`, each a list of
`{ id, volume, pitch, delayTicks? }` layers). They play positionally so nearby players hear
them. Every id was checked against the sound names the game's own `sounds.json` files
reference. To audition a change first: `/playsound <id> @s ~ ~ ~ <volume> <pitch>`.

### Law compass

`bountysys:law_compass` replaces the vanilla locator bar for law. Hold it in the main
hand and the action bar shows a bearing strip — `NEAREST  « ==========+===*====== »  Name  87m` —
pointing at either the nearest free outlaw or the one with the highest bounty. Sneak + use
switches between the two (same combo as reloading a gun, so it works on controller).
Free means not eliminated and not in jail.

- It's an action-bar readout rather than an item whose icon swaps: the script API has no
  way to change an icon in place, so it would take one inventory write per camera turn.
- Who to point at is decided about once a second and locked in
  (`COMPASS.retargetIntervalTicks`); only the bearing is recomputed on each 4-tick refresh.
  That's roughly a 75-85% cut in engine calls versus re-deciding every refresh.
- The game's main font (`minecraft-ten.ttf`) has no arrow or geometric-shape glyphs, so the
  strip only uses characters confirmed present (`=`, `+`, `*`, `«`, `»`). `=`, `+` and `*`
  share an advance width so the centered text doesn't shift as the marker moves.

### Train (in progress)

The old train (`train.ts`) is a set-piece: a structure re-loaded in hops along one straight
stretch, carrying nobody. `transit.ts` is its replacement, built in slices
(`docs/test-cards/TRAIN-RIDE.md`):

- The route is **recorded in game**, at track height, by walking it: `/scriptevent
  rae:train_mark`, `rae:train_station <name>`, `rae:train_undo`, `rae:train_clear`,
  `rae:train_loop`, `rae:train_info`, `rae:train_show` (draws it in particles). It is saved
  in a world property and smoothed into a curve (`logic/route.ts`).
- `bountysys:train_car` is a custom rideable entity (4 seats, invulnerable, no gravity or
  collision) that a script drives along the route. `rae:train_spike momentum|teleport` puts
  one car on the route and drives it each way, and `drag`, `limits` and `seats` measure what
  the engine does; the numbers go to the content log as `[train-spike]` lines.
- Its model and texture are generated: `node scripts/gen-train-model.mjs` (in `rae/`) writes
  them, and `npm test` fails if the committed files are not what it makes. To use a
  hand-made model instead, replace `models/entity/train.geo.json` and the texture and stop
  running the script.

Not built yet: the real train (an engine and several cars, stops at stations, waiting for
riders, leaving when none board) and the robbery on top of it.

## Building and testing

This targets a very recent engine build (`1.26.x` — the "26.x" marketing version, not
`1.21.x`). If you're on an older client, item/entity schemas may need adjusting; see
the format_version notes below.

```bash
cd rae
npm install         # once
npm run check        # type-check only
npm test              # compiles to .test-build/ and runs every test under a fake game API
npm run check:legacy  # the migration ratchet: fails if a count of an old pattern went up
npm run build         # compiles src/ into ../your_pack_name_BP/scripts/
```

**After any change that touches `items/`, `entities/`, or resource-pack content**,
bump the version in the relevant `manifest.json` (behavior pack and/or resource pack —
`header.version` and every `modules[].version`). This isn't optional: Minecraft caches
each pack's content by `(uuid, version)`, and separately, **every world that has the
pack applied pins the exact version it's using** in its own save data
(`world_behavior_packs.json` / `world_resource_packs.json` inside the world folder,
under `.../minecraftWorlds/<world>/`). Changing only the pack's own manifest does
nothing for a world that's already pinned to the old version — that pin has to be
bumped too, or the world keeps loading stale content indefinitely with no error. This
cost an entire debugging session to discover; don't skip it.

Plain script changes (no new items/entities) don't seem to need this, but bumping
anyway costs nothing and avoids finding out the hard way.

### In-game testing

```
/give @s bountysys:revolver
/give @s bountysys:handgun_ammo 64
```

Other guns: `pistol`, `bolt_rifle` / `rifle_ammo`, `semi_rifle` / `rifle_ammo`,
`pump_shotgun` / `shotgun_ammo`, `double_barrel_shotgun` / `shotgun_ammo`.

The compass (needs the `law` tag to work): `/give @s bountysys:law_compass`, or from a
command block `/give @a[tag=law] bountysys:law_compass`.

Debug commands: `/scriptevent rae:debug` lists every registered system and event id;
`/scriptevent rae:reset` forces a full round reset; `/scriptevent rae:adopt` reads every
player's role/status tags into the records now and lists what each record says.

## Known schema gotchas on this engine version (1.26.50+)

Discovered the hard way this session — current as of when this was written, may drift:

- `minecraft:icon` on items is a bare string (`"revolver"`), not `{"texture": "..."}`.
- Item `description.menu_category` is `{"category": "equipment"}` (nested), not a bare
  `"category"` string, once you're past the older 1.20.30-era item format.
- `minecraft:projectile`'s `anchor` field is a string (`"eye_height"`), not a number.
- `impact_damage.damage` is `{min, max}`, not a bare number.
- `should_bounce` is one of the strings `"no"` / `"if_invulnerable"` /
  `"if_no_damage_dealt"`, not a boolean.
- `minecraft:pushable` doesn't exist as an entity component in this schema — omit it. The
  vanilla boat and minecart have it, which makes it tempting to copy, but the game reports
  "found in the input, but is not present in the Schema" and the whole entity fails to load
  (seen on `bountysys:train_car` in BP 0.1.7, and the older note here was right all along).
  Vanilla entity JSON is not a safe template for what a custom entity may contain.
- **Vibrant Visuals needs `"capabilities": ["pbr"]` in the resource pack's manifest.** The
  game's own text says the mode "requires a PBR-enabled resource pack", and one active
  resource pack without the capability blocks it (the vanilla pack declares it; so does
  `BountySys_RP` since 1.0.16). Its `min_engine_version` must be 1.21.120 or higher (ours is
  1.26.50). Without texture sets our sprites and the train use the mode's default surface
  values; `assets.test.mjs` fails if the capability goes missing.
- `minecraft:rideable` seats can be an array of `{ position, min_rider_count, max_rider_count }`;
  the vanilla boat uses the counts to change its seat layout as riders board, and no vanilla
  entity has a fixed four-seat layout to copy. `bountysys:train_car`'s seats are a guess until
  the `rae:train_spike seats` measurement and a playtest.
- `Entity.applyDamage()`'s `cause: 'projectile'` requires the
  `{damagingProjectile: Entity}` overload — you can't pass a bare
  `{cause: 'projectile'}`; that throws at runtime. For hitscan damage with no real
  projectile entity, use a different valid cause (e.g. `entityAttack`).
- The dead entity in an `entityDie` handler can already be an invalid handle — calling
  `hasTag()` on it throws `InvalidEntityError`. `typeId`, `id` and `scoreboardIdentity`
  remain readable. Guard tag checks on it with `isValid`.
